# Earnings Q&A 봇 설계 (feasibility + design)

작성 2026-08-05. 상태: **설계 검토용 (미구현)**. transcript 아카이브 기반 RAG Q&A를
텔레그램 단체방에 붙이는 기능의 기술 검토와 구조 제안.

## 1. 요구사항 (사용자 요청 정리, 2026-08-05 스코프 확정)

1. 기존 Earnings 텔레그램 **채널 → 단체 채팅방**으로 전환
2. 방에 LLM 연결 (openclaw 유사 — 대화형 Q&A)
3. `/ask <질문>` 명령으로 질문·답변
4. RAG: **발간된 transcript 기반**. 특정 기업에 대한 질문이 오면 **그 기업의
   transcript를 참조**해 답변 생성. → **핵심·유일 범위**
5. **web search 는 배제** (일단 코어에서 제외. 훗날 필요 시 확장 후보로만 남김)
6. 답변 LLM: **미정** (Grok/Claude 등 — 아래 3장에서 옵션만 제시)

### 대표 시나리오
- 사용자: `/ask 엔비디아 데이터센터 매출 가이던스 어떻게 얘기했어?`
- 봇: 질의에서 **종목("엔비디아")** 인식 → 해당 기업 transcript(들) 검색 →
  관련 청크를 근거로 LLM이 답변 + 출처(분기·발표일) 인용
- transcript에 없는 기업/내용이면 "수집된 transcript에 없음" 으로 정직하게 응답

## 2. 결론: 전부 구현 가능. 난이도 낮음

핵심 근거는 **데이터 규모가 아주 작다**는 점.

| 항목 | 현재 | 의미 |
|---|---|---|
| transcript 파일 | 42건 (매일 +몇 건) | 1년 뒤에도 ~2,000건 수준 |
| 총 텍스트 청크 (500자) | 약 3,800개 | 벡터검색 없이 전량 스캔해도 즉답 가능한 크기 |
| 요약 md | 42건 | 답변용 짧은 컨텍스트로 바로 활용 가능 |
| 상시 가동 서버 | Mac mini (이미 24시간) | 봇 데몬 추가 비용 0 |
| LLM/키 | XAI 키 이미 보유 | 신규 인프라 불필요 |

이 규모에서는 무거운 벡터DB(FAISS/Chroma)조차 필수가 아니다. 단계적 접근이 낫다(6장).

## 3. LLM 옵션 (결정 보류 — 비교만)

| | Grok (기존 XAI 키) | Claude API | 하이브리드 |
|---|---|---|---|
| 추가 키/비용 | 없음 (재사용) | Anthropic 키 신규 | 둘 다 |
| 요약 파이프라인과 일관성 | 동일 스택 | 별도 | 부분 |
| web search | Grok Live Search 내장 | 별도 도구 연결 필요 | 유연 |
| 답변 품질 | 충분 | 최상급 | 질문별 최적 |
| 구현 복잡도 | 낮음 | 낮음 | 중 |

→ **결정 시 재론**. 어느 쪽이든 아래 구조는 그대로 쓰고 "답변 생성" 함수 하나만 갈아끼우면 됨(LLM 추상화 계층으로 분리).

## 4. 아키텍처

```
텔레그램 단체방
  ├─ [기존] 파이프라인이 어닝 요약 자동 발행 (변경 없음)
  └─ [신규] Q&A 봇 데몬 (launchd KeepAlive, Mac mini 상시)
       long-polling(getUpdates)으로 /ask 감지
        │
        ▼
   ┌─────────── ask_handler ───────────┐
   │ 1) 종목 인식(AI): 보유목록을 후보로   │
   │    LLM이 대상 기업 선택 → transcript  │
   │ 2) RETRIEVE: 그 기업 transcript에서  │
   │    질문 관련 청크 top-k 검색         │
   │ 3) GENERATE: LLM에 근거+질문 투입    │
   │ 4) 답변 + 근거(분기·발표일) 방에 회신 │
   │    (근거 없으면 "transcript에 없음")  │
   └────────────────────────────────────┘
        ※ web search 는 범위 밖 (미구현)
```

### 종목 인식 (2단계 핵심) — **AI 기반 매칭**
접근: 보유 기업 목록이 작으므로(현재 42, 1년 뒤 ~2,000) **전체 목록을 LLM에
후보로 통째 제공**하고 질의가 어느 기업인지 고르게 한다.

```
LLM 입력: 보유 기업 목록 [Apple Inc.(AAPL), NVIDIA Corporation(NVDA), ...전체]
          + 사용자 질문
LLM 출력: 정확한 회사명 1개 (목록에 없으면 "없음")
```

- 사전 관리 불필요. 한국어 통칭·티커·오타·모호 표현("엔비/그 GPU 회사")까지 매칭
- 후보를 **닫힌 목록으로 못박아** 환각(목록 밖 기업 생성) 차단 → "없으면 없음"
- 답변 생성과 동일 LLM 스택 재사용 → 구현 단순

**성능 절충(권장)**: ① 티커·정확한 영문명은 **코드로 즉시 매칭**(비용·지연 0)
② 애매할 때만 LLM 호출. 대부분 질문은 ①에서 끝나고 LLM은 진짜 모호할 때만.
- 매칭되면 검색 범위를 그 기업 파일로 좁혀 정확도·속도 확보
- 여러 분기 있으면 최신 우선(질의에 특정 분기 명시 시 그 분기)

### 데이터 흐름 (인덱싱)
- 기존 수집 파이프라인(`run_daily_pipeline.py`)에 **인덱싱 스텝** 1개 추가
- 새 transcript가 저장될 때 텍스트를 청크로 쪼개 인덱스에 append
- 인덱스는 로컬 파일 (`index/` — jsonl 또는 벡터스토어). Drive 업로드와 동일하게 실패 무해·재시도 구조

## 5. 컴포넌트별 기술 검토

### 5.1 채널 → 단체방 전환 (사용자 작업 필요)
- 텔레그램 UI에서 직접 수행 (봇 API로 채널을 그룹으로 바꿀 수 없음)
- **전환 시 chat_id가 바뀜** → 전환 후 `.env`의 `TELEGRAM_CHAT_ID` 갱신 + 파이프라인 전송 재검증 필요
- 봇을 그룹 관리자로 추가해야 메시지 발행·수신 가능
- 그룹에서 봇이 **모든 메시지**를 보려면 BotFather에서 privacy mode OFF 필요.
  단 `/ask` 명령만 받을 거면 privacy ON이어도 명령은 수신됨 → privacy ON 유지 권장

### 5.2 봇 상시 실행
- `scripts/qa_bot.py` 데몬을 launchd `KeepAlive=true`로 등록 (죽으면 자동 재기동)
- 파이프라인 launchd와 별도 label (`com.rootn.earnings-qabot`)
- long-polling이라 인바운드 포트·웹훅 불필요 (방화벽 설정 0)

### 5.3 RETRIEVE (RAG 검색) — 단계적 선택
- **A안 (초기, 추천)**: 임베딩 없이 **BM25/키워드 + 종목명 필터**. 3,800청크는 순수 파이썬으로 수십 ms. 의존성 0, 즉시 구현.
- **B안 (고도화)**: 임베딩(text-embedding) + 코사인 유사도. 표현이 다른 질문에 강함. `numpy`만 있으면 벡터DB 없이 가능(규모가 작아서). 임베딩 API 비용은 인덱싱 1회당 미미.
- 답변에는 반드시 **출처(기업·분기·발표일)**를 인용해 환각 억제

### 5.4 WEB search — **범위 밖 (미구현)**
- 이번 스코프에서 제외. transcript 근거만으로 답한다.
- 확장 후보로만 남김: 훗날 필요하면 GENERATE 앞에 보강 단계 추가(구조 영향 최소).

### 5.5 GENERATE (답변)
- LLM 추상화 함수 `answer(question, contexts, web) -> text` 하나로 격리
- 프롬프트: "아래 transcript 근거로만 답하고, 부족하면 모른다고 하라. 각 주장에 (기업, 분기) 인용" — 요약 파이프라인 프롬프트 규칙 재사용
- 텔레그램 4096자 제한 → 분할 전송(기존 `telegram_client` 재사용)

## 6. 권장 구현 순서 (단계적, 각 단계가 독립 동작)

1. **MVP**: `/ask <기업> <질문>` → 종목 인식 → 그 기업 transcript(전문) 키워드
   검색 → LLM 답변 + 출처. 개인 DM에서 테스트. web·임베딩 없음.
2. **종목 인식 강화**: manifest 별칭 사전으로 한국어 통칭·티커 매칭 정확도 향상.
3. **인덱싱 자동화**: 수집 파이프라인에 인덱싱 스텝 추가 (신규분 자동 반영).
4. **임베딩 검색**(선택): 키워드로 부족하면 도입.
5. **단체방 컷오버**: UI 전환 + chat_id 갱신 + 봇 관리자 추가 + 상시 데몬 등록.

→ 1단계만으로 "특정 기업 transcript 기반 Q&A"는 성립. 2~5는 정확도·운영 자동화.
→ **web search 는 순서에서 제외** (범위 밖).

## 7. 미결정·리스크

- **LLM 선택 미정** (3장) — 답변 함수만 영향, 구조 불변
- **비용**: 질문당 LLM 1회(+선택적 web/임베딩). 사용량 적으면 무시 수준. 폭주 방지용 rate limit 고려
- **단체방 chat_id 변경**: 전환 타이밍에 요약 전송이 잠깐 끊길 수 있음 → 전환 직후 즉시 갱신
- **환각**: 출처 인용 강제 + "모르면 모른다" 프롬프트로 억제. 완전 제거는 불가
- **권한**: 그룹 멤버 누구나 `/ask` 가능 → 필요 시 화이트리스트

## 8. 예상 산출물 (구현 시)

```
scripts/qa_bot.py              봇 데몬 (long-polling, /ask 핸들러)
scripts/qa_lib/
  resolver.py                  질의→종목 인식 (코드 즉시매칭 → 애매하면 LLM 선택)
  retriever.py                 대상 기업 transcript 청크 검색 (BM25→임베딩)
  indexer.py                   transcript→청크→인덱스 (파이프라인이 호출)
  llm.py                       answer() 추상화 (Grok/Claude 스위치)
index/                         로컬 검색 인덱스
com.rootn.earnings-qabot.plist launchd KeepAlive 데몬
```
(websearch 모듈은 범위 밖이라 산출물에서 제외)
